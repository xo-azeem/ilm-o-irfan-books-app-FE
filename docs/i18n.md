# Interface language (English / Urdu)

The app reads in English or Urdu. The choice lives on **Profile → Language**,
applies the moment a row is tapped, and is remembered across launches.

## Where the words live

```
src/i18n/
  locale.ts        LOCALES, LOCALE_META (name, script, BCP 47 tag), isArabicScript()
  current.ts       the current locale for code with no React in it
  localeStore.ts   the persisted choice (MMKV, key `ilm-locale`)
  strings/
    index.ts       strings(locale?) and dateLocale() — for services
    en/*.ts        the English copy, one file per feature — the source of truth
    ur/*.ts        the Urdu copy, typed against the English object
  index.ts         useStrings(), useLocale(), useDateLocale() — for components
```

Every screen reads `const s = useStrings()` and then `s.home.greeting`,
`s.reader.sheet.bookmark` and so on. A string that takes values is a
function: `s.reader.pageOf(page, total)`. Services and other non-React code
call `strings()` at the moment they need a sentence (never at module load),
so an error thrown from a service is already in the reader's language.

The Urdu files are declared `typeof en`, so **adding a string to English
without its translation is a compile error**, and removing one takes the
translation with it. Add the English first, then the Urdu.

## Script, not language, decides the face

`Text`, `Display` and `Label` look at the text they are drawing: a run in the
Arabic script is set in Nastaliq with the extra leading it needs, no
letter-spacing (tracking breaks Arabic joins) and right-to-left direction.
An Urdu interface therefore still shows English book titles and addresses
in DM Sans, and an English interface shows Urdu titles in Nastaliq — nothing
at a call site has to know which language is on.

The layout itself is not mirrored. Urdu text right-aligns in its own box;
rows, icons and gestures keep their positions. Full `I18nManager` mirroring
needs an app restart and an audit of every absolute layout, and is a
separate piece of work.

## Dates and numbers

`useDateLocale()` / `dateLocale()` give the tag (`en-GB`, `ur-PK`) to pass to
`toLocaleDateString` and friends. Digits stay Western in both languages.

## Across devices

The choice is kept twice. The device keeps it in MMKV so the first frame is
already in the right language, signed in or not. A signed-in reader's account
keeps it too, on `profiles.locale`, written by `useSaveLocale` the moment a
row is tapped on the Language screen and read back with the profile.
`LocaleSyncProvider` reconciles the two: signing in on a device that has
never seen the account adopts the account's language (or, if the account has
none yet, records the device's); a change made on another device arrives with
the next profile read and the device follows it. A change made on this device
never bounces back, because the save writes the new value into the cached
profile before the server answers.

## What the backend composes

Every API request sends `Accept-Language` with the interface language, and
the home feed's rail headings ("Because you read …", "More by …") come back
in it — the `recommendations` function passes it to the SQL that composes
them, falling back to the account's saved language.

Still English, deliberately: push notification titles and bodies, deletion
blockers, and data readers typed themselves — names, book titles, plan names.

## Switching

Choosing a language re-renders every screen at once. The few sentences the
services write into cached data (a read time, "Page 6 of 424") were composed
in the old language, so the Language screen also invalidates the query cache
and everything re-reads in the background.
